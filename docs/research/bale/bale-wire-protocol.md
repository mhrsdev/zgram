## 1. Transport summary

Two transports reach the same backend host family:

1. **grpc-web over HTTPS (unary)**, content type `application/grpc-web+proto`. Base URL in production: `https://next-ws.bale.ai`. Used for **every call of `bale.auth.v1.Auth`** regardless of mode, and for all services when the client is in "grpc" mode (iOS before login, or after the WebSocket was judged unstable).
2. **Binary WebSocket**, URL `wss://next-ws.bale.ai/ws/`, protocol name "mkproto" version 1, API version 1. All other services' unary calls are tunnelled as `ClientPack.request` frames; server pushes arrive as `ServerPack.update` frames.

Endpoint selection (module 28184), by page host:

| Condition | grpc base | ws URL |
|---|---|---|
| host contains `web.bale.ai` (production) | `https://next-ws.bale.ai` | `wss://next-ws.bale.ai/ws/` |
| host is `beta.bale.ai` | `https://beta-ws.bale.ai` | `wss://beta-ws.bale.ai/ws/` |
| any other host (internal / staging) | `https://maviz-ws.bale.ai` | `wss://maviz-ws.bale.ai/ws/` plus `?uid=<id of the user saved in localStorage "user">` when logged in |
| local dev proxy mode | `/api` | `ws(s)://<page host>/wss` |

Mode selection (module 6835, `getConnectionMode`): every platform except iOS uses `ws`. iOS uses `grpc` until `localStorage.isLoggedIn == "true"`, then `ws`.
Module 84458 class `Api.unary`: if mode is `grpc` **or** the method belongs to service `bale.auth.v1.Auth` use grpc-web, else if mode is `ws` use the WebSocket. A remote config (see 1.1) can additionally disable individual RPCs, in which case the call is silently skipped.

The WebSocket falls back to grpc mode (`onFail`) when the connection flaps: if more than 15 s passed since `startTime` and the average per-open time is under 5 s **(inferred from the arithmetic; `startTime` initialisation was not located)**.

## 2. grpc-web call format (exact)

Implementation chain: service client method (`this.rpc.unary(methodDescriptor, request, metadata?)`) -> `Api.unary` (84458) -> class `m.unary` -> `grpc.unary` of `@improbable-eng/grpc-web` (47319) -> `CrossBrowserHttpTransport({withCredentials: true})` = `fetch` with `credentials: "include"` when `fetch` + streams are supported, XHR with `withCredentials = true` otherwise.

Request:

* `POST {base}/{serviceName}/{methodName}`, e.g. `POST https://next-ws.bale.ai/bale.auth.v1.Auth/StartPhoneAuth`. Package-qualified service name exactly as in the `.proto` `package` + `service`.
* Headers: `content-type: application/grpc-web+proto`, `x-grpc-web: 1`, plus the metadata of section 1.1 (lower-cased header names) and optional per-call metadata merged over them. **No `authorization` header, no `grpc-timeout`, no `x-user-agent`.**
* Body: one grpc-web frame: 1 byte flag `0x00`, 4 bytes big-endian payload length, then the protobuf bytes of the request message (empty requests are `00 00 00 00 00`).
* Credentials: the session is carried by browser cookies (`credentials: include`) **(inferred; see 6.1)**. The code never reads or writes `document.cookie` and never attaches a bearer token. `saveToken` is `false` for the web build, so the JWT returned by login is not persisted (section 3.6).

Response:

* Body is a sequence of frames. Flag byte `0x00` = a data frame (response protobuf). Flag bit `0x80` = trailers frame containing `name: value\r\n` lines.
* Status is taken from the `grpc-status` response header if present (trailers-only responses), else from the trailers frame; if none, from the HTTP status: 0->Internal, 200->OK, 400->InvalidArgument, 401->Unauthenticated, 403->PermissionDenied, 404->NotFound, 409->Aborted, 412->FailedPrecondition, 429->ResourceExhausted, 499->Canceled, 501->Unimplemented, 503->Unavailable, 504->DeadlineExceeded, else Unknown.
* `grpc-message` is URI-decoded and becomes the error message.
* Extra user-facing text: trailer `grpc-status-details-bin` (base64, a `google.rpc.Status`; field 3 = repeated `Any{type_url=1, value=2}`). The `Any` whose `type_url` ends with `/google.rpc.LocalizedMessage` carries `{locale=1, message=2}`; the trimmed `message` is exposed as `displayMessage`.
* Error object: `{message, code (grpc status number), displayMessage}`. gRPC code numbers: OK 0, Canceled 1, Unknown 2, InvalidArgument 3, DeadlineExceeded 4, NotFound 5, AlreadyExists 6, PermissionDenied 7, ResourceExhausted 8, FailedPrecondition 9, Aborted 10, OutOfRange 11, Unimplemented 12, Internal 13, Unavailable 14, DataLoss 15, Unauthenticated 16.
* `Unauthenticated` (16) on any grpc call triggers `forceSignOut()` (clears local state), **except** for `bale.ramz.v1.Ramz/CheckPassword`.

Retry policy of the higher-level wrapper (module 21410 / 92972, used by the typed clients): per-attempt timeout 15 s, up to 10 retries, exponential back-off starting at 1 s doubling to a cap of 60 s, retried only for gRPC codes Canceled, Unknown, DeadlineExceeded, ResourceExhausted, Aborted, FailedPrecondition, Internal, Unavailable and for timeouts.

### 3.2 ValidateCode

Request `ValidateCodeRequest`: 1 `transactionHash` string; 2 `code` string (the OTP the user received); 3 `isJwt` BoolValue (the web client always sends `true`); 4 `futureAuthTokens` repeated string (web sends empty); 5 `language` int32 enum `Language` (UNKNOWN 0 by default).

Response `ValidateCodeResponse` (shared by ValidateCode, ValidatePassword and SignUp): field 2 `user` (`User`, section 3.7), field 3 `config` `{maxGroupSize int32 = 1}`, field 4 `jwt` StringValue. Field 1 is unused. Calls fail with a gRPC error when the code is wrong; the client enumerates the strings `PHONE_CODE_INVALID`, `PHONE_NUMBER_UNOCCUPIED` and `password needed for login` as known error texts (module 72593) **(their use is in the unsaved UI chunk; presumably compared against the grpc message)**.

### 3.3 ValidatePassword (two-step verification)

Used when `activationType == PASSWORD` (or the server demands a password). Request `ValidatePasswordRequest`: 1 `transactionHash`, 2 `password` string, 3 `isJwt` BoolValue (web: true), 4 `language`. Response: `ValidateCodeResponse`.

### 3.4 SignUp

Used when `isRegistered == false`. Request `SignUpRequest`: 1 `transactionHash`, 2 `name` string, 3 `sex` int32 enum (UNKNOWN 0, MALE 1, FEMALE 2; web sends 0), 4 `password` StringValue (web sends nothing), 5 `language`. Response: `ValidateCodeResponse`. After SignUp the client saves the user but passes **no** token to storage.

### 3.5 Order of calls

1. `StartPhoneAuth(phone, appId=4, apiKey, deviceHash, deviceTitle, sendCodeType, options)` -> keep `transactionHash`.
2. Code path: `ValidateCode(transactionHash, code, isJwt=true)`.
3. If the server requires it: `ValidatePassword(transactionHash, password, isJwt=true)`.
4. If the number is new: `SignUp(transactionHash, name, ...)`.
5. On success the client writes to `localStorage`: `user` (JSON of the returned `User`), `isLoggedIn = "true"`; `token_bale` only if `saveToken` is true (it is `false` on web). It then (inferred: the call site is in the app shell, not in the saved files) runs `Core.start()`, which opens the WebSocket (section 4) and, once connected, calls `ChangeLanguage` if a language was chosen, then loads configs/dialogs/presence.
6. `Auth.SignOut` (empty) clears the server session; errors are ignored and local state is wiped anyway. `Auth.LogOut` returns `futureAuthToken` StringValue (a "remember this device" token, usable later with `activationType = FUTURE_AUTH_TOKEN` / `sendCodeType = FUTURE_AUTH_TOKEN` and `ValidateCode.futureAuthTokens`) **(inferred; no caller in the saved code)**.

### 3.6 Tokens, JWT, tickets

* `isJwt=true` makes the server include `jwt` in the validate response. On the web build it is read but **not stored** (`saveToken=false`); the browser session cookie is what persists the login **(inferred)**. Non-web builds (`saveToken=true`) store it under `localStorage["token_bale"]`.
* There is **no token refresh RPC** in the saved client. `GetJWTToken` (empty request -> `{jwt: StringValue}`) can mint a JWT for the logged-in session; no call site exists in the saved code, so its purpose (mini-apps / external services) is **(inferred)**.
* Tickets for other Bale services: `GetBaleTicket{expDateTime int64, mobileNo string, clientId string} -> {redirectUrl}`, `GetBajeBamTicket{expDateTime, mobileNo} -> {ticket}`, `GetTicket{jsonRequest, jsonSign} -> {redirectUrl}`, `GetUserIdToken{ticket} -> {token, userId, source, service}`. `expDateTime` is a client-supplied expiry, JS number serialised as int64.
* Two-factor management: `IsTwoFactorAuthenticationEnabled`, `EnableTwoFactorAuthentication{email,password}`, `VerifyEmail{email,code}`, `VerifyPassword{password}`, `DisableTwoFactorAuthentication`, recovery by `RecoverPassword{transactionHash} -> {emailPattern}` -> `VerifyPasswordRecovery{code, transactionHash}` -> `SetNewPassword{newPassword, transactionHash}`.
* Sessions: `GetAuthSessions -> userAuths[{id, authHolder (THISDEVICE 0 / OTHERDEVICE 1), appId, appTitle, deviceTitle, authTime, authLocation, latitude, longitude, lastActivityAt, lastIpAddress{text}}]`, `TerminateSession{id}`, `TerminateAllSessions`.
* A separate, app-level password ("Ramz" service): `SetPassword`, `CheckPassword{password, servicesType} -> {token}`, `SendOTP`, `ValidateOTP`, `CheckPasswordSet`, ... (see table).

### 3.7 `User` object returned at login

`User`: 1 id int32; 2 accessHash int64; 3 name; 4 localName; 5 sex; 6 avatar (`Avatar`); 7 isBot; 9 nick; 14 ext (map string -> `Value`); 15 stateVersion; 16 isDeleted; 17 contactInfo (repeated {type, stringValue, longValue, title, subtitle, typeSpec}); 18 puppeteer; 19 createdAt; 20 exInfo (`ExPeerInfo`: exPeerType, peerIdentity, peerCategory); 21 botExInfo. `UserOutPeer{uid int32 = 1, accessHash int64 = 2}` is how users are addressed in most later calls.

## 4. WebSocket protocol

Module 84458, class `el` ("WS"). Protobuf definitions: `protos/websocket.proto`.

### 4.1 Connecting

* `new WebSocket(url)` with **no subprotocol list** and **no token in the URL** (production). `binaryType = "arraybuffer"`; all frames are binary protobuf, one `ClientPack` / `ServerPack` per frame, no extra framing.
* How the session is presented: nothing in the JS adds credentials, so the browser sends its cookies on the upgrade request **(inferred)**. The staging URL appends `?uid=<id>`. The React-Native variant sets `Origin: https://web.bale.ai`.
* Open timeout 3000 ms, then `reconnect()`.

### 4.2 Envelopes

`ClientPack` (client -> server): `request = 1`, `ping = 2`, `handshakeRequest = 3`.
`ServerPack` (server -> client): `response = 1`, `update = 2`, `terminateSession = 3`, `pong = 4`, `handshakeResponse = 5`.

| Message | Fields |
|---|---|
| ClientPack.Request | 1 serviceName string, 2 method string (method name only), 3 payload bytes (serialized request message), 4 metadata (`MetadataItems`: repeated {key string, value `Value`{stringValue = 1,...}}), 5 index int64 |
| ClientPack.Ping | 1 ID int64 |
| ClientPack.HandshakeRequest | 1 mkprotoVersion int32, 2 apiVersion int64 |
| ServerPack.Response | 1 error optional bytes, 2 response optional bytes, 3 index int64 |
| ServerPack.Update | 1 update bytes |
| ServerPack.Pong | 1 ID int64 |
| ServerPack.HandshakeResponse | 1 mkprotoVersion int32, 2 apiVersion int64, 3 serverTime int64 (ms epoch) |
| ServerPack.TerminateSession | empty |
| ApiError (the bytes in `Response.error`) | 1 code int32, 2 message string, 3 details (`MetadataItems`; the item with key `message` and `stringValue` is the user-facing text) |

### 4.3 Handshake

On socket open the client sends `ClientPack{handshakeRequest{mkprotoVersion = 1, apiVersion = 1}}`. Both constants are literals in the code (`ProtocolVersion = 1`; `apiVersion` constructor argument = 1). Wire bytes: `1a 04 08 01 10 01`.
It waits for `handshakeResponse`; per attempt timeout 1000 ms; up to 5 retries with back-off 200 ms..5000 ms, only after a timeout. If the response's `mkprotoVersion != 1` or `apiVersion != 1` the client calls its force-update callback and does not proceed. On success the client computes a clock offset `round(serverTime - (tSend + tRecv)/2)` and monkey-patches `Date.now()` with it (all later timestamps/ids are server-corrected). A `serverTime` of 0 is ignored. Only then the state becomes `connected`, `reconnectId` resets to 0 and ping/pong starts. (A configuration flag `shouldHandshake` exists; the web build passes `true`.)

### 4.4 Ping/pong

Every 10 s (RxJS `interval(10000)`, first tick after 10 s) the client sends `ClientPack{ping{ID = n}}` where `n` counts 0, 1, 2, ... per connection. (`ID = 0` is omitted by proto3 so the first ping is `12 00`.) After each ping it waits up to 5 s for **any** `pong` (the ID is not compared). On a timeout or error it closes the socket, which triggers reconnect. The server sends `pong{ID}`.

### 4.5 RPC over WebSocket

`ws.unary(descriptor, request, metadata?)`:

1. If not `connected`, wait until it is.
2. `index = ++counter` (starts at 1, never reset, survives reconnects).
3. Send `ClientPack{request{index, serviceName, method = methodName, metadata = headers as in 1.1 (plus per-call), payload = request.serializeBinary()}}`. The values of a header with several entries are joined with a space.
4. Match the first `ServerPack.response` whose `index` equals the request index. `error` and `response` are *optional* bytes (field presence matters, an empty `response` is a valid empty message). If `error` is present -> decode `ApiError` and fail; else if `response` is present -> decode with the method's response type; else fail with "Invalid response". There is no timeout inside this layer; the calling wrapper applies the 15 s timeout and retries (section 2).
5. If the socket is not open at send time: close, reconnect, fail the call with `{code: 2, message: "Socket is not ok: <service>, <method>"}`.

### 4.6 Close, errors, reconnect

* Close code **4401** = unauthenticated: no reconnect, `onUnauthenticated` -> `forceSignOut()` (local sign-out). Any other close code, any socket error, an open timeout, a handshake failure, or a ping timeout -> `reconnect()`.
* `ServerPack.terminateSession` -> same as 4401, then the socket is closed by the client.
* Reconnect delay: attempt number `n = reconnectId` (0 at first): `0` ms if `n == 0`, else `min(100 * 2^(n-1), 3000)` ms, i.e. 0, 100, 200, 400, 800, 1600, 3000, 3000, ... ms. `reconnectId` is reset on a successful handshake. A pending reconnect timer blocks duplicates. When the tab becomes visible again and the socket is CLOSED, or it is not connected and a reconnect was pending, the timers are cleared and a reconnect is started immediately.
* Decode failures of an incoming frame are logged and ignored.

### 4.7 `update` frames

`ServerPack.update` has one field `bytes update = 1`. Subscribers (`ws.invoke(descriptor, ...)`) simply try `descriptor.responseType.deserializeBinary(update)` on every frame and drop the ones that throw; **no request is sent** for an `invoke`. So after the handshake the server pushes frames spontaneously, and each frame's `update` bytes are the serialized **response message of a server-streaming method** (in grpc mode the same method is a real server-streaming call, with auto-retry after 3 s on selected codes). That method descriptor is not in the saved files; it is declared in the lazy chunk that builds the core (section 5). What can be said from the saved files:

* The update objects handled by the saved code carry presence-style fields such as `parameterChanged{key, value}` (config parameter changes, `Configs.EditParameter` response model).
* Mutating RPCs return an `EditParameterResponse{seq int32 = 1, state bytes = 2, seqBig int64 = 3}`; the same triple (`SeqState{seq, date, state, ext, seqBig}`) is the sequence/state token for gap-free update delivery **(inferred)**.
* Message models usable inside updates are in section 5.2.
* Practical decoding approach for a captured frame: strip the `ServerPack` wrapper with `protos/websocket.proto`, then run `protoc --decode_raw` on `update`.

## 6. Open questions and what was tried

1. **How the WS/grpc session is authenticated.** Searched all saved chunks for `authorization`, `bearer`, `cookie`, `token`, `x-`; the only token-like state is `token_bale` (guarded by `saveToken`, false on web) and the `jwt` in the validate response. `fetch` uses `credentials: "include"` and `new WebSocket(url)` has no extra arguments, hence the cookie conclusion (inferred). A capture of the `Set-Cookie` after `ValidateCode` would confirm it.
2. **`deviceHash` / `deviceTitle` generation** and which `sendCodeType`/`options` are chosen: lives in the unsaved `Login` chunk.
3. **Callers of `GetJWTToken`, `futureAuthTokens`, `LogOut`**: none in the saved code.
4. **The server-streaming update method and its response (the `update` payload) type**: only in the unsaved core-builder chunks (`62663` and dependencies). `invoke` proves the payload is that method's response message.
5. **Messaging RPCs** (send/edit/delete/history/typing/read/reactions): not present, see section 5.
6. **Enum-typed fields.** The codec decodes enums with a plain int32 read, so field-to-enum links are lost; the `.proto` files keep `int32` and add "enum?" hints from names only. Enum definitions themselves are fully recovered in `protos/enums.proto` (75 enums).
7. **Units** of several timestamps/waits (`codeExpirationDate`, `nextSendCodeWaitTime`, `expDateTime`): not stated in code.
8. **Whether the WS `ApiError.code` uses gRPC numbering**: the grpc path does; the WS path builds the same error object, so it very likely does **(inferred)**.
9. **The 15 s / 5 s flap detector** that switches to grpc mode (`startTime` initialisation not found).
10. Whether groups such as `MessageContent` members or `Value{stringValue, booleanValue, int32Value, int64Value, doubleValue, arrayValue}` are protobuf `oneof`s cannot be seen (ts-proto flattens them into optional fields). The `.proto` lists them as ordinary fields (scalars with presence as `optional`); semantically set only one.
11. Message names in the `.proto` files are derived (RPC role names; inferred shape names such as `Peer`, `Dialog`; otherwise `Msg_<module>_<local>`); only field names, numbers and wire types are authoritative.
